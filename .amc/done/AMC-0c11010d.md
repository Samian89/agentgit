# AMC-0c11010d — Merge model ADR and cherry-pick (review cycle 5)

## What I built this cycle

Review 1 from this round had a placeholder reason; in lieu of a
specific complaint, I audited the implementation against the spec's
"no partial mutation in the target session" guarantee and closed the
remaining runtime-error gap that the dry-run pass alone did not cover.

### Change this cycle — atomic apply pass

The cherry-pick had a two-pass design since cycle 2: a dry-run that
detects path-level conflicts before any writes, then an apply pass
that writes new commits one by one. The dry-run guarantees that
**conflict**-driven failures cannot leave partial state. But the apply
pass walks N source commits and calls `Repository.commit` for each;
if a runtime error fires between, say, step 2 and step 3 of a 5-step
replay (disk full, missing blob object, lock contention), the first
two commits had already been inserted into SQLite and the session
head had advanced — a partial mutation that violated the acceptance
criterion for any non-conflict failure mode.

Fix in `packages/core/src/cherry-pick.ts`: the apply loop is now
wrapped in `repo.index.transaction(() => { ... })`. `better-sqlite3`
nests transactions via SAVEPOINTs, so the inner transactions that
`Repository.commit` opens still commit individually, but throwing
anywhere in the outer block rolls every commit row, tree-entry row,
and session-head update back to the pre-cherry-pick state. The thrown
error is caught and surfaced as a `CherryPickError` result so callers
get a uniform discriminated-union to switch on instead of an
exception bubbling out of the SDK. Filesystem objects written before
the rollback remain content-addressed and unreferenced — GC reclaims
them on the next `agentgit gc` run.

### New regression test

`cherryPick — apply-pass atomicity > rolls back every commit when a
mid-replay blob read fails` in
`packages/core/src/__tests__/cherry-pick.test.ts`:

1. Sets up a clean 2-step source on top of a shared base; target
   forks off the base.
2. Sabotages the on-disk object file for one blob that the second
   replayed commit will need to read (the dry-run only inspects the
   index, so it doesn't notice — the failure surfaces in pass 2).
3. Asserts that the cherry-pick returns `status: "error"`, the
   target session head is unchanged, the target session's commit
   count is unchanged, and the target branch ref still points at
   the pre-cherry-pick head.

Without the transaction wrap, the first replayed commit would have
been left in the session and the test would fail. With it, the
rollback is clean.

### Reviews 2 + 3 — still covered by prior cycles

- **Review 3 (mid-chain conflicts invisible at source head)** —
  resolved in cycle 2. The per-step dry-run compares each step's
  `prev[P] → curr[P]` change against the simulated `dryState`, so
  modify-then-revert and add-then-remove patterns that erase
  themselves from the final source-head tree still raise a conflict
  at the offending step. Regression tests
  `cherryPick — mid-chain conflict invisible at source head` cover
  both shapes.
- **Review 2 (writes outside CONFLICT + disjoint-history CLI
  crash)** — resolved in cycles 3+4. `CherryPickConflict.mergeBase`
  is `Hash | null`; the CLI branches on null and prints `(no common
  ancestor — disjoint histories)` rather than crashing on
  `shortHash(null)`. `isSafeConflictPath` rejects empty paths,
  absolute paths, `/` and `\` rooted paths, Windows drive-letter
  prefixes (`C:foo`), NUL-byte paths, and anything whose resolved
  form doesn't have `conflictDir + sep` as a prefix; rejected paths
  are surfaced via `CherryPickConflict.unsafePaths`. Regression
  tests `cherryPick — disjoint histories` and `cherryPick — path
  traversal hardening` (three cases: `..`, absolute, drive-relative)
  cover both.

## APIs, types, or interfaces other tickets may consume

Stable surface (unchanged this cycle):

- `Repository.mergeBase(a: Hash, b: Hash): Hash | null`
- `Repository.cherryPick(input: CherryPickInput): CherryPickResult`
- `CherryPickInput`, `CherryPickResult`, and its four variants
  (`CherryPickOk`, `CherryPickConflict`, `CherryPickNoop`,
  `CherryPickError`) exported from `@agentgit/core`
- CLI: `agentgit merge-base <a> <b>` and
  `agentgit cherry-pick <source> --onto <target> [--session <name>]`
- `.agentgit/CONFLICT/<path>` directory layout on conflict
- Commit metadata key `metadata.cherryPickedFrom = <sourceHash>` on
  every replayed commit
- `CherryPickConflict.mergeBase: Hash | null`,
  `.conflictingStep: Hash`, `.unsafePaths: string[]`

New behaviour callers may rely on this cycle:

- A runtime failure in the apply pass (e.g. a deleted source-side
  blob object, a SQLite lock, a disk error) now returns
  `{status: "error", message: "cherry-pick apply pass failed and was
  rolled back: <cause>"}` rather than propagating an exception, and
  is guaranteed to leave the target session and any matched branch
  ref exactly as they were before the call. Consumers can rely on
  the same uniform `CherryPickResult` switch they already use for
  the conflict/noop branches.
